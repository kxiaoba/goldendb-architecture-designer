# GoldenDB 60台服务器用例测试与修正报告

日期：2026-10-26；原源码基线：e8681e185c15c1f59bab686fba6cd3cbfc23be7a。

## 1. 已确认的输入与解释

- 本地A、同城B各30台；不是两座城市，不能抵御城市级灾害。
- 3个租户分别24、3、1分片。分片数原样保留，1分片仍按本次用户指定的分布式租户及专属GTM规划，不擅自删除GTM。
- 每租户业务CN合计6个，各机房3个；额外共用运维CN合计2个，各机房1个。运维CN单独占用物理服务器，其跨租户连接能力、授权和资源模型待产品版本确认。
- 经用户确认：每租户独立GTM，3个Group各6副本，共18个；允许跨租户CN共享物理服务器。
- 管理6副本；DN每分片6副本；每一副本组每机房各3个。所有正常运行主在本地A。单个管理节点按一个逻辑组件计数，未将CM/PM/MDS内部进程拆成多个“组件”。
- 仅CN与GTM混布；不同租户DN可以共宿。管理、运维CN独立；DN与CN/GTM分开。同租户CN跨物理机，同DN/GTM Group副本跨物理机。
- 每服务器所有逻辑组件实例合计不超过4；不将“单机最多4个DN”当作全组件上限。

## 2. 结论与数量复算

结构可行，生产准入未评估。每机房30台恰好容纳，无空闲物理服务器。

|租户|分片|DN总数|本地/同城DN|业务CN|专属GTM|
|---|---:|---:|---:|---:|---:|
|租户1|24|144|72/72|6|6|
|租户2|3|18|9/9|6|6|
|租户3|1|6|3/3|6|6|
|合计|28|168|84/84|18|18|

另有管理6个、运维CN2个。总组件=168+18+18+6+2=212。DN主28个、DN从140个；GTM主3个、从15个；管理按逻辑角色标注1主5从。

|组件池|本地A服务器|同城B服务器|本地A组件|同城B组件|
|---|---:|---:|---:|---:|
|DN共享池|21|21|84|84|
|管理专用池|3|3|3|3|
|CN/GTM混布池|5|5|9CN+9GTM|9CN+9GTM|
|运维CN专用池|1|1|1|1|
|合计|30|30|106|106|

在上述隔离边界内，每机房必要台数下界=ceil(84/4)+3+ceil(18/4)+1=21+3+5+1=30。本次最大流求解实际构造出完整落位，并由独立枚举核对212个ID，因此该下界在本例可达。这个最少台数仅针对本次池隔离及实例数量，不是生产性能最优或全局可靠性最优。

## 3. 原工具发现的问题及修正

1. **确定的计算错误**：`buildReverseTenantPlans`对手工分片强制取偶，24/3/1变成24/4/2，DN由应有168误算180。修复为保留已通过整数校验的手工输入；业务自动推荐分片的取偶开关不变。
2. **输入能力缺失**：原入口没有CN+GTM定向混布、单机全组件总上限、额外运维CN，无法完整表达该用例。新增“固定数量约束设计”入口，显式记录每租户CN/DN/GTM数量，使用最大流装箱和独立审计；不借用“全混布”绕过原生产红线。
3. **管理主从缺少显式标注**：原工具只有同名“管理节点”角色。新入口逐实例编号并标注逻辑主从及机房，且保留“管理6副本及选主规则未核验”，不假称已满足产品高可用要求。
4. **输入歧义**：若沿用原工具生产CN跨租户物理隔离，本例在其他池独立时每侧21+3+9+1=34台，总计至少68台。用户已明确允许跨租户CN共宿，故本结果60台成立。
5. **不足状态必须保留**：58台、禁止CN/GTM混布且仍60台、禁止跨租户CN共宿且仍60台，均拒绝输出成功清单或成功组网图；不突破机房/密度/反亲和约束兜底。

原工具复现采用了128C/1024GB的**测试夹具假设**，仅为减少资源水位对数量缺陷复现的干扰，并非用户硬件。按最终独立GTM口径，原工具显示DN180、GTM18、业务CN18、管理6、无运维CN，并提示不足；旧算法估算80台、实际只落位164组件。这不是与新方案同约束的80→60优化：新入口增加了原来不存在的跨租户CN/GTM共享策略，不能据此声称节省25%生产资源。

## 4. 组网与逐实例输出

`部署清单.html`含可打印完整60台清单、每个DN分片和副本、CN归属、GTM归属、主从及逻辑组网；`完整落位.json`为统一结构化数据；`逻辑组网.svg`为逻辑关系图。

应用访问CN；CN与所属租户GTM和DN交互；管理/监控接入各组件；A-B存在管理、GTM、DN复制/控制链路。物理交换机、IP、VIP/DNS、端口、VLAN、带宽/RTT和防火墙矩阵未提供，不能称物理组网已验收。图中的两侧CN可被访问，不表示同一分片双主写；当前主均在A。

## 5. 生产准入待办

- 指定GoldenDB版本/补丁，取得管理1主5从及3+3分布、Team、复制/选主/隔离策略的厂商依据。官方公开金融应用指南典型建议管理3或5副本；本用例6副本是待核验要求，不静默修改。
- 普通六投票成员多数派需4票，3+3在失去一侧后不足4；但不能直接用该推理断言GoldenDB实际不可用，其增强协议/Team/管理HA实现必须按版本确认。网络分区、机房失效、回切均需实测。
- 提供每主机CPU/内存/净磁盘、RAID/日志/索引/工作区预算、实例配额及license；单机4个DN并不自动适合64C机器。若每DN假设16C，4个DN已占64C，尚未留安全余量，这只是资源算术提示，不是厂商固定规格。
- 提供数据量、增长、TPS/QPS、SQL/事务、热点、批次及备份/重建负载，验证双中心接管、存储/IO/网络、容量/性能、RPO/RTO。
- 60台全部分配。240个逻辑槽位减212=28个空槽位，分散在控制/运维/CN池内，不能视为28个DN槽位或空闲机器；故障重建源/目标和共享空间未评估。
- 运维CN跨租户服务能力/权限、访问路由及资源隔离需验证；仅保留两个节点不代表运维功能已交付。

## 6. 验证记录

- 新结构模型与独立实例枚举：36/36；包含边界、无效输入、同名租户、篡改、密度1至6、58/60/64/68台及不允许混布分支。
- 浏览器专项：19/19；真实JSON/HTML/SVG下载，输入变更清除旧结果/禁用导出，390/875/1600宽度，无脚本异常。
- 现有回归：主分布61/61、反推身份/状态26/26、逐Group数据30/30。合计已通过172项。
- 双方全新浏览器会话比较，原有业务/反推默认完整数据及落位与原版一致。
- 对HTML实际60行服务器、JSON212个实例、SVG每侧数量核对；新脚本与原app语法检查通过。
- 这是规划工具测试；没有连接真实GoldenDB或执行生产部署。未进行新增入口XLSX导出，也不把结构通过当作原工具全部遗留项已关闭。

## 7. 文件与修复使用

修正版从原工具首页的“固定数量约束设计”进入，或打开`fixed-constraints.html`。该入口为固定数量/等量双机房结构设计，原业务测算与资源反推保留，用于其既有范围；两个入口的生产/性能结论不可混用。
