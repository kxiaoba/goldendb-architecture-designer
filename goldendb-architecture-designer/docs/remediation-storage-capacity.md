# V3a 磁盘净容量与旧口径迁移

日期：2026-10-19。V3a限定范围已本地验收，保留V2c修改；用户随后授权将两批一起提交并推送。推送结果以git-release.json为准，不等同Pages部署完成。

## 本批范围

业务测算的各组件增加显式legacy/net口径。默认legacy维持原始盘总量乘(1-统一预留)，不改旧方案数量。net模式按同容量盘、独立热备、RAID、文件系统比例、每主机日志/索引/临时空间预留、独立磁盘水位计算；同一损耗不再重复扣统一预留。需求继续用原有租户/逐Group数据，不擅自添加数据增长或把索引预算重复计入数据需求。

RAID仅建模RAID0/单盘、RAID5与经典双副本成对RAID10；不声称覆盖任意软件RAID布局。未知RAID阻止生成净容量结果，经典RAID10要求有效盘数为不小于4的偶数，是本模型支持范围而非所有mdadm布局的产品限制。RAID0不允许热备，且明确无冗余。预算必须留有正可用容量，不能以0.1TB等下限垫高。

净口径作为物理主机规格一部分，机型统一选取时一起继承；混部组件口径或空间预算不同不能套用旧“推荐机型均兼容”的快捷判断。实际宿主机按其真实规格独立计算。原始diskTb字段保留原意，净容量由统一函数派生。

## 影响和待办

本批联动单机适配、数量估算、候选五布局、逐Group落盘、CPU/内存不变、资源水位、风险、计算说明、摘要及Excel。磁盘百分比在net模式相对文件系统扣除后的可分配数据空间，水位单独比较；不把raw盘百分比冒充净空间占用。

反推模块本批仍保留旧口径，并明确缺少业务数据量和净容量承载验收；不能新增一个看似通过但需求仍为0的“净磁盘承载”。V3b继续反推的显式业务数据需求、净容量输入、三年规划和故障空间预算；V3c补完整跨模块矩阵。完整计划在remediation-backlog.md。

## 独立复算与验证结果

8块2TB盘、热备1、RAID5：7有效盘扣1份校验，阵列12TB；文件系统预留10%后10.8TB；日志1TB、索引0.5TB、临时0.3TB后9TB；磁盘水位80%后7.2TB。即使CPU/内存统一预留35%，磁盘不再乘0.65。CPU、内存仍各乘0.65。

同盘数/热备/RAID、奇偶、0/空/负数/非有限/预算耗尽、旧口径不漂移、预留改变不重复影响net磁盘、模式切换/重置/草稿、统一机型与混部兼容、逐Group最大空间和实际装箱、Excel逐格及手机桌面截图均需验证。

参考源码：[mdadm md.4](https://github.com/md-raid-utilities/mdadm/blob/main/md.4)、[mdadm.8](https://github.com/md-raid-utilities/mdadm/blob/main/mdadm.8.in)。已核对RAID0无冗余、RAID5校验和热备与活动盘分离、RAID10双副本及非经典奇数布局存在，因此不将本模型的成对限制当作通用厂商事实。不是GoldenDB性能或特定RAID控制器兼容认证。
