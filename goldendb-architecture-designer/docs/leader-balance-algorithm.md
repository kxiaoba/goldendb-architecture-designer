# DN主分片均衡算法与适用条件

日期：2026-10-28；P01。实现：leader-balance.js，入口GoldenDBLeaderBalance.solve。用于生成初始部署设计，不连接GoldenDB，也不执行在线切主或副本迁移。

## 目标、节点和范围

“节点主数量差≤1”适合作为同等承载能力下的基础计数目标。它不等于TPS、CPU、IO或热点均衡；异构服务器、分片冷热/大小差异、在线与跑批混合负载需要另做实测权重与故障接管预算。

节点指物理DN宿主机，不是同机多个DN进程。先按租户的正常主中心策略确定每个Group的目标AZ，再在同AZ、允许资源池中优化；不为均衡改变主中心、减少副本或借用其他AZ。容灾站点正常0主不与生产站点混算。

- 单AZ：在该租户允许使用的DN池主机间均衡，包括0主的机器；仍不具备机房级故障冗余。
- 多AZ、主固定A：只在A内均衡，B保持0主；原60台用例执行此规则。
- 多AZ、生产中心均衡：沿用既有Group主中心配额，分别在每个生产AZ内均衡。不能因各AZ主机数不同而擅自改变既定主中心配额。
- 独立租户池不跨池；禁止跨租户DN共宿时，其他租户已占用的专用主机不计为可用范围。CN、GTM、管理、运维CN和无DN池配置的空库存不计为DN均衡节点。
- 范围与候选不同：范围可包含0主/无该租户副本的DN池主机；某Group只能选该组已规划同AZ副本所在主机为主。没有副本的主机不能凭空获得Leader。分布结果必须显示这些0主，不能缩小分母制造“均衡”。

## 两层实现

固定数量模式的初始副本构造：保留原整数最大流的Group→宿主机容量1及宿主机组件上限；DN组候选边从第i台起循环枚举，避免每个租户都集中使用前一小段机器。轮转只调整新建布局的候选顺序，不改变管理/CN/GTM/运维CN的构造规则。轮转是启发式，不能据此声称任意输入均衡必然可达。

随后执行有界最小费用流。通用业务/反推模式使用已经完成的副本布局直接执行此步骤，不再尝试跨Group交换。最终同一Group在各主机的副本集合保持；只在同AZ同Group间交换初始主/从设计标签。

图结构：源→Group→租户-主机→主机→汇。每Group流量1；Group只能连入合法候选主机；显式locked的Group只保留当前主边。租户-主机和主机到汇采用单位容量凸费用边。

令N为参与Group数量，B为其他固定主总数；l(t,h)为某租户在该AZ/主机上的主数量，L(h)为所有租户主总数（含固定主），M为改变初始主位置的Group数量。按以下优先级优化：

1. 最小化Σ l(t,h)²，先满足租户均衡；
2. 在1的最优解内最小化Σ L(h)²，避免每个租户都把余数放到同一机器；
3. 前两项相同则最小化M，避免不必要变化，保证再次执行不抖动。

整数权重：Wg=N+1；Wt=(N+B)²×Wg+N+1。费用为Wt×Σl²+Wg×ΣL²+M，固定常数不影响最优解。两权重分别大于所有低优先级项的最大可能差，因此不是任意调参的混合打分。第k条单位边费用对应k²−(k−1)²=2k−1；包含固定主的主机边使用2(Bh+k)−1。内部费用用BigInt避免整数溢出，报告不输出BigInt。

```text
核对唯一ID、目标域、候选、副本及锁定条件
建立凸费用候选网络
用势函数+Dijkstra逐次寻找最短增广路径
若达到工作/边数预算：返回未完成，保留原方案，不应用部分流
完整流完成：提取每Group唯一主宿主机
核对租户/全池主数量、目标AZ、同Group宿主机与资源不变量
全部校验通过后一次性应用到初始设计
```

在候选网络完整求解的范围内，算法得到上述计数目标的最优解；不是所有副本重新布局、容量与网络联合问题的全局最优解。若同一约束范围存在全部租户差≤1的解，租户平方和达到其数学下界；否则结果显示constrained与实际差值，提示调整副本布局/容量/策略。不能把constrained等同于“物理扩容无解”。

## 状态和安全边界

|状态|含义与动作|
|---|---|
|balanced|完整求解且租户和同域合计差都≤1，仅计数目标通过|
|constrained|完整求解，但至少一个范围仍偏斜；保留实际差值与候选约束，不伪称均衡|
|budget-exceeded|超过200万工作步或5万正向边预算；无部分assignment输出，原方案保持|
|invalid / unavailable / rejected|输入/模块/应用后核验异常；不应用结果|
|not-needed|无参与Group，无切换动作|

2000主机/2000Group等上限仅为浏览器交互保护，不是GoldenDB产品限制。输入与报告解耦，稳定ID排序保证相同输入可复现；元数据数组顺序不影响最终选择。

通用模式仍要求副本完整、主中心正确、允许池/隔离/密度/资源水位通过才参与；缺项租户保持原状并提示未评估。当前主从使用相同资源规格估算，交换后预算不变不代表真实主从负载相同。固定数量模式仍仅做结构规划，缺硬件预算时不会升级为容量/生产验收通过。

R18的既有实例锁定规则继续生效：本算法不会用于改写现网基线；即使solve支持locked输入，也不等于已经接入增量规划。运行中Leader切换需要版本支持、复制追平、健康状态、变更窗口与回退验证；本批未产生这类命令。

## 可借鉴来源与独立验证

- [TiKV PD的balance_leader源码](https://github.com/tikv/pd/blob/master/pkg/schedule/schedulers/balance_leader.go)：参考其从Follower候选出发、过滤节点/放置约束，并将热点与一般Leader计数调度区分的思路。PD在线调度协议、Raft规则和参数不能直接套用于GoldenDB；本实现没有复制其调度代码。
- [Google OR-Tools最小费用流实现说明](https://github.com/google/or-tools/blob/stable/ortools/graph/min_cost_flow.h)：用于核对流守恒、最小费用目标、整数费用与求解状态概念。这里独立实现逐次最短路，没有引入OR-Tools运行依赖或声称采用其同一种内部算法。
- tests/leader-balance.cjs以240个小图穷举所有合法Leader选择，独立计算三层目标，逐例与求解器对照；另检验锁定、跨AZ、未知候选、预算、幂等及80组固定数量构造。UI专项核对单/多AZ、同Group宿主机保持、实际JSON/HTML/SVG及Excel模型输出。最终计数与哈希见本批验收记录。

页面风险与Excel主角色分布共用evaluationStatus：缺少求解记录、预算耗尽或未验证的租户均为未评估；逐租户差值达标但同池所有租户合计仍偏斜时显示提示，不将单租户结果误作整体通过。
